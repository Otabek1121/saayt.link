# Независимое размещение Saayt.link в Cloudflare

## Состояние

Код подготовлен и проверен локально. Production в Sites продолжает работать отдельно.
Новый Worker, D1, R2, Google OAuth и перенос production-данных требуют настройки аккаунта.
Не переключать домен до проверки кабинета, публикаций, QR и файлов на новой инфраструктуре.

## Первичная настройка

1. В Cloudflare создать D1 `saayt-link-db` и приватный R2 bucket `saayt-link-media`.
2. В `wrangler.jsonc` заменить `database_id` на ID созданной D1.
3. Создать Worker `saayt-link` с подключением GitHub `Otabek1121/saayt.link`.
4. Для проверки использовать его адрес `https://saayt-link.<ваш-поддомен>.workers.dev` в `PUBLIC_SITE_ORIGIN`. После переезда вернуть `https://saayt.link`.
5. В Google Cloud создать OAuth client типа Web application. Разрешить callback `<PUBLIC_SITE_ORIGIN>/api/auth/google/callback`. Для тестового и основного адреса нужны отдельные разрешённые callback URL. Опубликовать приложение либо добавить тестовых пользователей.
6. В Worker → Settings → Variables and Secrets добавить секреты `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `SESSION_SECRET` (случайное значение минимум 32 символа). Не хранить их в GitHub и не пересылать в чат. При необходимости добавить те же имена в build secrets для интеграционных проверок; сборка не нуждается в OAuth-секретах.
7. Применить миграции: `pnpm db:migrate:cloudflare`.

## Автоматическая публикация из GitHub

Cloudflare Workers Builds, production branch `main`, root `/`:

- Build command: `pnpm run build:cloudflare`
- Deploy command: `pnpm run deploy:cloudflare`
- Node: 22.13+; pnpm берётся из `packageManager`.

Сначала настройте D1 ID и проверьте ветку `cloudflare-migration` на отдельном Worker. Автоматическое применение миграций не включено: новые миграции применяются перед выпуском использующего их кода.
`deploy:cloudflare` останавливается, пока в конфигурации остаётся тестовый D1 ID.
Сборка использует `vite.cloudflare.config.ts`, `worker/cloudflare.ts` и генерирует `dist/server/wrangler.json`. Старый `build` оставлен для исходного Sites.

## Перенос данных

- Получить свежий экспорт всех таблиц из текущей базы. Старый JSON backup сначала сверить с актуальной схемой и количеством записей.
- Импортировать projects, media, guest_entries, studio_members, сохраняя ID, owner, public_slug, published, revision и связи. Восстанавливать в пустую D1 в порядке внешних ключей. Резервные копии и клиентские данные не коммитить в публичный репозиторий.
- Скопировать каждый файл R2 с исходным object key и Content-Type, затем сверить размеры/контрольные суммы с экспортом. Публичные демонстрационные картинки уже входят в код; это не замена пользовательским загрузкам.
- Для каждого прежнего пользователя установить подтверждённое соответствие его Google email и прежнего ID в `auth_legacy_identities`. Таблица доступна только оператору базы; публичного endpoint для её заполнения нет. Значения email должны быть в нижнем регистре. Нельзя назначать старого владельца на основании непроверенной строки из запроса.
- Сохранять прежние ID сотрудников, чтобы действующие права не потерялись. Новые пользователи без соответствия получают ID `google:<sub>`.

## Проверка и переключение

Проверить вход/выход, отсутствие доступа без сессии, права владельца и сотрудника, создание/редактирование/публикацию, загрузки и галерею, публичные URL, QR, гостевые формы, карту сайта и все языки. Затем остановить изменения на старом сайте, сделать финальный перенос, сверить записи/объекты и переключить домен на Worker. Держать прежнее размещение и резервную копию до завершения проверки. Не отключать Sites заранее.

`pnpm test`

`pnpm run build:cloudflare`
